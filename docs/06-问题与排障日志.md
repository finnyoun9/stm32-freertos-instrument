## 常见方向速查（先怀疑这些）

| 类别 | 先查 |
| --- | --- |
| 一进调度器就 HardFault | 中断向量映射、优先级分组、`configPRIO_BITS`、栈大小 |
| 任务不切换 | 优先级配置、`vTaskDelay` 有没有、是不是死循环不让出 |
| 串口乱码 | 波特率、时钟配置（HSE 是否起振）、`printf` 重定向 |
| 中断里调用 API 后跑飞 | 用了非 `FromISR` 版本 / 中断优先级过高 |
| 内存分配失败 | `configTOTAL_HEAP_SIZE`、是否泄漏、碎片 |
| LCD 花屏/无显示 | **先怀疑 `lcd.a` 授权校验**（该库含 `licio.c`/`rsa.c`/`xor_encrypt.c`，见 `firmware/README.md`）→ 再查初始化时序、背光、数据宽度 |
| 采样波形失真 | 采样率不足、参考电压、输入阻抗、DMA 缓冲覆盖 |

## 2026-09-18 · vision-router 把默认模型改成包装 provider，导致所有 headless 调用失败

> ⚠️ 这条不属于 STM32 项目本身，是**开发机工具链**的坑。记录在此是因为它**直接导致本项目记忆系统的摘要功能静默失效**。

- **现象**：MemSearch 维护任务报 `dsh: NO_ADAPTER: no adapter registered for provider "deepseek-vision"`；`dsh --profile headless "..."` 任何调用都失败。
- **影响**：所有依赖 `dsh --profile headless` 的功能全挂 —— 包括 MemSearch 的会话摘要（`summarizeMode: auto` → `dsh-headless`）。表现为记忆只捕获不摘要。
- **假设**：
  1. `~/.dsh/settings.yaml` 的默认模型指向了一个在该 profile 不存在的 provider；
  2. headless profile 缺少某个 bundle；
  3. DSH 版本与插件不兼容。
- **验证**：
  1. 读 `~/.dsh/settings.yaml` → `agent-default-model.provider: deepseek-vision`。✅ 命中假设 1
  2. 跑 `dsh-vision-router doctor` → 输出 **`headless — Vision Router not installed in this profile`**。证明 `deepseek-vision` 是 vision-router 注册的**包装路由**，只存在于 desktop profile。✅ 根因确认
  3. 查 adapter 实际注册名 → `deepseek-official`（来自 `@deepseek-ai/dsh-llm-deepseek`）。❌ 排除假设 2、3
- **结论**：**根因** —— `dsh-vision-router` 的 onboarding 把 `agent-default-model.provider` 从真实 provider `deepseek-official` 改成了它自己的包装路由 `deepseek-vision`。该路由仅在 desktop profile 由插件注册；`headless`/`web` profile 没有这个插件，于是解析 provider 时直接 `NO_ADAPTER`。
  这是**跨 profile 的配置耦合陷阱**：桌面端能选到的模型，不等于其它 profile 也能用。
- **修复**：把 `~/.dsh/settings.yaml` 改回真实 provider：
  ```yaml
  agent-default-model:
    provider: deepseek-official   # 原为 deepseek-vision
    model: deepseek-flash
    reasoningEffort: high
  ```
  改后 `dsh --profile headless "只回答两个字：正常"` → 输出 `正常`；MemSearch 维护任务恢复正常。
  （改前的 settings 备份在 `/tmp/settings.yaml.bak-visionrouter`，仅本机临时目录）
- **遗留**：
  - `deepseek-vision` 的**视觉能力并未丧失** —— 模型选择器里的 `(DeepSeek-V4-Flash (vision))` 变体仍可选，只是不再作默认。需要粘贴图片时手动选它。
  - 若希望**默认即带视觉**，vision-router 提供了 `stealth: true` 选项（接管官方 `deepseek-official` 路由，见其 README 配置表），可避免包装 provider，从而与 headless 兼容。**未采用**：接管官方路由影响面更大，需正式评估。
  - 教训：**装任何会改写 `settings.yaml` 的插件后，先验一遍 `dsh --profile headless`**。

## 2026-09-18 · 8KB 托管堆的余量可能偏紧

- **现象**：尚未观察到现象（前瞻性风险）。
- **影响**：堆用尽时 `pvPortMalloc` 返回 NULL，任务创建或队列创建静默失败；后期加软件定时器、队列、事件组时会撞上限。
- **假设**：`configTOTAL_HEAP_SIZE = 8192`（L283）需要容纳 4 个任务栈（2560 B）+ TCB（约 368 B）+ 空闲任务栈（512 B）+ 定时器任务栈（约 1024 B），估算已占 ≈ 4556 B，余量 ≈ 3636 B（约 44%）。
- **验证**（待做）：打开 `configUSE_TRACE_FACILITY`（L373）+ `configUSE_STATS_FORMATTING_FUNCTIONS`（L380），用 `xPortGetFreeHeapSize()` / `xPortGetMinimumEverFreeHeapSize()` 读真实数字，并用 `demo.map` 核对 TCB 实际大小。
- **结论**：待填（**估算值未经验证，不得写进简历**）。
- **修复**：待定（可能需把 `configTOTAL_HEAP_SIZE` 提到 12288/16384）。
- **遗留**：确认软件定时器任务是否真的计入堆。
- **证据**：待补 → `docs/evidence/`

## 2026-09-18 · tick 分辨率 10ms 导致的延时时序偏差

- **现象**：尚未观察到现象（设计选型，非缺陷）。
- **影响**：`pdMS_TO_TICKS()` 对小延时取整。`configTICK_RATE_HZ=100`（L78）时 1 tick = 10ms，故 `pdMS_TO_TICKS(5)` 得 0（等价于不阻塞），按键扫描等周期性动作的实际周期存在抖动。
- **假设**：`key_task.c` 的 `vTaskDelay(pdMS_TO_TICKS(10))` 恰好 = 1 tick，实际周期受 tick 对齐影响。
- **验证**（待做）：任务入口翻转一个空闲 IO，用示波器/逻辑分析仪量实际周期；再改 `configTICK_RATE_HZ` 为 1000 对比。
- **结论**：待填。
- **修复**：待定（若确需更细精度则改 1000Hz，注意 tick 中断开销上升）。
- **遗留**：面试需能解释「为什么 100Hz 够用 / 什么场景必须调高」。
