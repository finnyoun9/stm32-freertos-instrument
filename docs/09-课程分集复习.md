## 1.1 理查德巴利与 FreeRTOS（P2）→ `docs/03` 第 1 条

- **是什么**：FreeRTOS 由 Richard Barry 于 2003 年发起并长期维护，后由 Real Time Engineers Ltd 运营，2017 年起由亚马逊托管（AWS FreeRTOS）。MIT 许可。
- **为什么存在**：裸机 `while(1)` 里塞全部逻辑，一旦要"同时"做 LCD 刷新 + 按键扫描 + ADC 采样，任何一处阻塞都会拖死全盘。RTOS 把这件事变成「每个任务写自己的死循环，调度器决定谁跑」。

> **面试点**：FreeRTOS 是 **RTOS，不是通用 OS** —— 没有 MMU、没有用户态/内核态隔离、没有内存保护。所有任务共享一个地址空间，一个任务写飞全系统崩。这既解释了它为什么轻量（内核约 6–10KB Flash），也是它的软肋。
> 🔍待确认：内核 Flash 占用的具体数字，请用你工程的 `demo.map` 实测后替换，别用我这个通用估值。

## 1.4 初次使用 FreeRTOS（P5）→ 第 4 条（🟡 缺串口日志）

代码事实（`Core/Src/main.c` L134-137）：

```c
xTaskCreate(vKeyTask,    "Key",    128, NULL, 3, NULL);  // 优先级 3
xTaskCreate(vBuzzerTask, "Buzzer", 128, NULL, 1, NULL);
xTaskCreate(vLCDTask,    "LCD",    256, NULL, 1, NULL);  // 栈最大
xTaskCreate(vLEDTask,    "LED",    128, NULL, 0, NULL);  // 优先级 0
vTaskStartScheduler();
```

**`xTaskCreate` 六个参数**（顺序别记错）：

| 参数 | 你的值 | 含义 |
| --- | --- | --- |
| `pxTaskCode` | `vKeyTask` | 任务函数，原型固定 `void f(void*)`，**绝不能 return**（返回会触发 `prvTaskExitError` 死循环） |
| `pcName` | `"Key"` | 调试用名字，受 `configMAX_TASK_NAME_LEN` 限制 |
| `usStackDepth` | `128` | **单位是 word（4 字节），不是字节** → 128 word = 512 B |
| `pvParameters` | `NULL` | 传给任务的参数 |
| `uxPriority` | `3` | 数字越大优先级越高（0 最低） |
| `pxCreatedTask` | `NULL` | 回传句柄；传 NULL 表示后面不引用它 |

> ⚠️ **发现 1（真实风险）**：`configMINIMAL_STACK_SIZE` 在 `FreeRTOSConfig.h` L115 是 **128**，单位同样是 **word**。
> 你的 `vLEDTask`（128 word）**刚好等于最小合法栈**。若任务内使用 `printf` 或浮点，栈会溢出。
> 这条对应 `docs/08` 里的「任务栈余量查不了」——不是形式主义，是真隐患。

**缺的证据**：一段串口日志，证明 4 个任务都跑起来了、tick 在跳。这是第 4 条从 🟡 变 ✅ 的最小成本动作。

## 2.1 FreeRTOS 总图（P6）→ 第 5 条（☐）

内核全景（后续每一章都是这张图的展开）：

```
        ┌──────────── 应用层：你的 4 个任务 ────────────┐
        │  Key(3)   LCD(1)   Buzzer(1)   LED(0)        │
        └───────────────────┬───────────────────────────┘
                            │ 调用
        ┌───────────────────┴───────────────────────────┐
        │                 内核核心                       │
        │  tasks.c         任务管理与调度                │
        │  list.c          就绪/阻塞/挂起链表            │
        │  queue.c         队列（信号量/互斥量的底座）   │
        │  timers.c        软件定时器                    │
        │  event_groups.c  事件组                        │
        │  heap_4.c        内存管理                      │
        └───────────────────┬───────────────────────────┘
                            │ port 层（移植层）
        ┌───────────────────┴───────────────────────────┐
        │  port.c   SVC / PendSV / SysTick 三个异常      │
        └───────────────────────────────────────────────┘
```

> **关键认知**：**信号量、互斥量、队列、邮箱，底层共用 `queue.c` 同一套结构**。
> 你 `docs/03` 第 26 条的 `xSemaphoreForDMA`，本质是一个「长度 0、数据大小 0」的队列。想通这点，第六章和第七章能一起打通。

## 2.3 配置文件（P8）→ 第 7 条（✅）

我核对过 `Core/Inc/FreeRTOSConfig.h` 的实际值：

| 宏 | 行号 | 你的值 | 含义 |
| --- | --- | --- | --- |
| `configCPU_CLOCK_HZ` | L54 | 72 MHz | 内核时钟，决定 SysTick 计数 |
| `configTICK_RATE_HZ` | L78 | **100** | 1 tick = **10ms** |
| `configUSE_PREEMPTION` | L83 | 1 | 抢占式调度 |
| `configUSE_TIME_SLICING` | L90 | 1 | 同优先级时间片轮转 |
| `configMAX_PRIORITIES` | L109 | **5** | 优先级 0~4，**0 是最低** |
| `configMINIMAL_STACK_SIZE` | L115 | 128 word | 空闲任务栈 |
| `configTOTAL_HEAP_SIZE` | L283 | **8192 B** | 8KB 托管堆 |
| `configUSE_MUTEXES` | L621 | 1 | 启用互斥量 |
| `configUSE_COUNTING_SEMAPHORES` | L623 | 1 | 启用计数信号量 |

### ⚠️ 发现 2：tick 分辨率偏粗

`configTICK_RATE_HZ = 100` → tick 周期 **10ms**。
你 `key_task.c` 里写 `vTaskDelay(pdMS_TO_TICKS(10))`，正好等于 1 个 tick。
**任何小于 10ms 的延时都会被取整**（`pdMS_TO_TICKS(5)` → 0，会变成"不阻塞"），时间抖动较大。

- 这**不是 bug**，是选型。课程用 100Hz 是为了让初学者容易在逻辑分析仪上看到 tick。
- 但要在面试里说清：**为什么 100Hz 够用 / 若要更细的延时精度该改什么**（改成 1000Hz，代价是 tick 中断开销上升）。
- 🔍待确认：课程是否在其他章节调整过这个值，请回看确认。

### ⚠️ 发现 3：8KB 堆的账，需要实测确认

`configTICK_RATE_HZ=100` 之外，更值得注意的是堆预算。heap_4 的 **8192 字节含 TCB + 各任务栈**：

| 项 | 估算 | 依据 |
| --- | --- | --- |
| 4 个任务栈 | (128+128+256+128) word × 4 B = **2560 B** | `main.c` L134-137 |
| 4 个 TCB | 4 × ~92 B ≈ **368 B** | `tasks.c` 的 `TCB_t` 大小 |
| 空闲任务栈 | 128 word × 4 B = **512 B** | `configMINIMAL_STACK_SIZE` |
| 空闲 TCB | ≈ **92 B** | |
| 定时器任务（若启用） | ≈ **1024 B** | `configTIMER_TASK_STACK_DEPTH` |
| **小计** | **≈ 4556 B** | |
| **剩余** | **≈ 3636 B（约 44%）** | 留给队列/信号量/事件组/动态分配 |

> 🔍待确认：TCB 大小和定时器任务是否真的计入，请用 **`demo.map` + 打开观测宏后的实测数字**替换我这个估算。**估算值不许写进简历。**

## 2.4 安装中断服务程序（P9）→ 第 8 条（✅，你唯一做实的一条）

代码事实（`Core/Startup/startup_stm32f103rctx.s` L144/147/148）：

```asm
.word vPortSVCHandler        ; 原本是 SVC_Handler
.word xPortPendSVHandler     ; 原本是 PendSV_Handler
.word xPortSysTickHandler    ; 原本是 SysTick_Handler
```

**这三个异常是 FreeRTOS 接管 CPU 的全部开关**，机制各不相同：

| 异常 | 何时触发 | FreeRTOS 用它做什么 |
| --- | --- | --- |
| **SVC** | 启动调度器时执行 `svc 0` | **启动第一个任务**：从 PSP 恢复任务上下文，切入线程模式 |
| **PendSV** | 软件置位 `ICSR.PENDSVSET` | **任务上下文切换**：保存当前任务上下文入栈、恢复下一个 |
| **SysTick** | 每 10ms 硬件自动触发 | **心跳**：tick +1，检查有无任务该唤醒，需要切换就挂起 PendSV |

> **面试高频**：为什么上下文切换放在 PendSV，而不直接在 SysTick 里切？
> 因为 PendSV 可设为**最低优先级**，切换会推迟到所有中断处理完毕后再执行，避免在中断嵌套中切换任务导致栈混乱。
> 你的证据：`docs/evidence/20260918-vector-table/`（ELF 向量表实测）。这一条做得对。

## 3.1 变量的作用域和生命周期（P10、P11）→ 第 9 条（☐）

这一集是**为理解栈做铺垫**，不是 C 语言扫盲课。核心一张表：

| 存储类 | 生命周期 | 存放在哪 | 例子 |
| --- | --- | --- | --- |
| `auto`（局部变量） | 函数进入 → 退出 | **栈** | `void f(){ int x; }` |
| `static`（函数内） | 程序全程 | `.data` / `.bss` | 函数退出值仍保留 |
| `static`（文件级） | 程序全程 | `.data` / `.bss` | 仅本 `.c` 可见 |
| `extern` | 程序全程 | `.data` / `.bss` | 跨文件共享 |
| `malloc` | 手动释放 | **堆** | FreeRTOS 里换成 `pvPortMalloc` |

> **和 RTOS 的连接点**：每个任务有**自己独立的栈**。所以任务函数里的局部变量存在**该任务的栈**上，不是"全局栈"。
> 这正是 `usStackDepth` 必须给够的原因——你 `vLCDTask` 给 256 word、别的给 128，就是因为 LCD 里有较大的局部数组/浮点运算。

## 3.2 变量在 SRAM 里的分布（P12）→ 第 10 条（☐）

STM32F103RCT6 的 48KB SRAM，链接后的布局（低地址 → 高地址）：

```
0x20000000 ┌───────────────────────────┐
           │  .data   已初始化全局变量  │  ← 启动时从 Flash 拷贝
           ├───────────────────────────┤
           │  .bss    未初始化全局变量  │  ← 启动时清零
           ├───────────────────────────┤
           │  heap    （向上生长 ↑）    │  ← heap_4 的 8192 B 在这里
           ├───────────────────────────┤
           │          空闲              │
           ├───────────────────────────┤
           │  stack   （向下生长 ↓）    │  ← 主栈 MSP
0x2000C000 └───────────────────────────┘
```

> ⚠️ **FreeRTOS 下有两套栈，这是理解中断与任务的关键**：
> - **MSP（主栈指针）**：中断处理使用，即上图向下生长的那个 stack
> - **PSP（进程栈指针）**：每个任务自己的栈，从**堆**里分配
>
> 任务运行时用 PSP；一旦进中断，硬件自动切到 MSP。这就是 `docs/08` 里「中断 → 任务链路时序」要抓的底层原因。

**证据做法（极低成本）**：编译后的 `demo.map` 直接给出各段地址与大小。这条从 ☐ 变 ✅ 只需要看一次 map。
🔍待确认：具体 SRAM 大小以你 `demo.map` / 数据手册为准（我按 F103RC = 48KB 记，请核对）。

## 3.3 堆 / 3.4 栈（P13、P14）→ 第 11 条（🟡）

| | 栈 (stack) | 堆 (heap) |
| --- | --- | --- |
| 分配方式 | 编译器自动 | 手动 `pvPortMalloc` |
| 释放 | 函数返回自动 | 手动 `vPortFree` |
| 生长方向 | **向下**（高→低地址） | **向上**（低→高地址） |
| 速度 | 极快（只改寄存器） | 慢（需查找空闲块） |
| 大小 | 编译期确定 | 运行期动态 |
| 你的配置 | 主栈 + 每任务独立栈 | `heap_4`，8192 B |

**FreeRTOS 的任务栈是什么**：`xTaskCreate` 时从堆里 `pvPortMalloc` 一块内存，并把它初始化成"看起来像刚被中断打断"的伪造栈帧。这样第一次调度到该任务时，`portRESTORE_CONTEXT` 直接"恢复"它即可运行。

**heap_4 的算法**：首次适应（first fit）+ 相邻空闲块合并。相比 `heap_2` 多了合并，因此抗碎片；相比 `heap_5` 不支持多块不连续内存。
你 `docs/03` 第 24 条选 `heap_4` 的理由（有删除/释放需求且要抗碎片）是对的。

## 3.5 FreeRTOS 代码规范（P15 之前）→ 第 12 条（🟡）

匈牙利式前缀，你代码里已全在用：

| 前缀 | 含义 | 你的例子 |
| --- | --- | --- |
| `v` | 返回 void | `vKeyTask`、`vLCDTaskInit` |
| `x` | 返回 `BaseType_t` / 句柄 | `xDmmData`、`xSemaphoreForDMA` |
| `ux` | 无符号基础类型 | `uxPriority` |
| `prv` | private（`static`） | `prvCalcDMMValue` |
| `pd` | 宏 | `pdMS_TO_TICKS`、`pdTRUE` |
| `config` / `INCLUDE_` | 配置宏 | `configTOTAL_HEAP_SIZE` |
| `port` | 移植层 | `portYIELD_FROM_ISR` |

**类型命名**：`TickType_t`（tick 计数）、`BaseType_t`（返回值，通常 int）、`UBaseType_t`（无符号）、`TaskHandle_t`（任务句柄）。
**别把 `int` 和 `BaseType_t` 混用**，换平台会出问题。
